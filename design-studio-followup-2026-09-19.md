## 2. Findings

Each finding leads with **what the user sees**.

### N1 — Roofline anchor setup: Preview / Apply don't work

There is **no control literally labelled "Apply to My Lights"** anywhere in `lib/` (grep, case-insensitive). The two screens where anchors are actually set — `segment_setup_screen.dart` and `roofline_setup_wizard.dart` — **import no device code at all**. The report therefore maps onto two real flows, and **both are broken, in different ways.**

#### N1a — "Find LED on Controller → Light It Up" is a stub that fakes success
**User sees (installer):** Roofline Setup Wizard → step 4 **"Verify Anchor Points"** → the prominent **"Find LED on Controller — Light up specific LEDs to verify positions"** → type an LED number → **Light It Up**. A **green** bar says *"LED 42 should now be lit red on the controller."* **Nothing on the roof changes.** The dialog even says *"Ensure the controller is connected and online."*
**Failure mode:** the handler contains no device call. Its own comment: `// Note: This would need a connected repository to work` / `// For now, show a message about what would happen`. It validates the number and shows the snackbar. The file has no import of `wled_providers`, `per_pixel`, or any repository.
**Evidence (CODE):** `lib/features/design/roofline_setup_wizard.dart` — button `:1154-1160`; dialog `:2535`; stub + comment `:2581-2591`; "Light It Up" `:2605`; imports `:1-14`. Installer-only gate `:180-185`. Entry: System → My Lights → **Setup Wizard** (`system_management_screen.dart:410`).
**Does it share F7's shape?** No — it is worse. F7 *sends* the writes and discards the results. This sends **nothing** and reports success. It was **not bench-tested because there is nothing to test**: no payload exists.
**Why it matters beyond itself:** this is the tool an installer would use to *find* corners and peaks. The original audit's F5 (zero corners/peaks in 31/31 production segments) has a contributing cause here: the verification aid on the anchor step never worked.
**Working reference implementations exist:** `installer/screens/map_roofline_step.dart:70-145` and `design/refine/refine_roofline_screen.dart:74-135` both light real LEDs through `PerPixelWriter.applyPerPixel` and snapshot/restore prior state.

#### N1b — Setting an anchor re-bases every segment; the editor then paints the wrong LEDs  ← ties to root cause B
**User sees (any user, 2+ channel home):** Design Studio → **Roofline setup** (the button pinned above both AI and Manual modes) → **Edit Anchors** on a segment → tap a couple of LEDs → Done → Save. Back in **Manual**, tap **Anchors**, **Paint**, turn on **Preview on lights** / press **Apply to Lights**. Green **"Applied to your lights."** The house goes **dark except for a couple of LEDs in a place they never marked** — or fully dark. On a single-channel home this works, which makes it look intermittent.
**Failure mode:** `toggleAnchor → updateSegment → RooflineConfiguration.updateSegment → recalculateStartPixels()`. That last function runs **one counter across all segments regardless of channel** (the F4 writer), so *any* anchor edit rewrites channel 2's first segment from `start_pixel 0` to `start_pixel = (channel 1's total)`. The editor's `anchorIndices` then computes `seg.startPixel + anchor` and treats it as **channel-local**; `PixelDesignDocument.paint` **silently drops** out-of-range indices; `applyBaseAndSpans` sends the near-black base plus whatever survived and returns `true` (F7).
**The original audit found this seam in stored data (5 of 7 channel≥1 docs cumulative). This pass identifies what writes it: the anchor editor itself, on every tap.**
**Evidence (CODE, real classes):** a correct channel-local 2-channel map (ch1 = 128, ch2 = 162). User sets anchors at the two ends of the channel-2 segment:

| | ch2 segment `startPixel` | `anchorIndices(ch2)` | pixels actually painted |
|---|---|---|---|
| Before the edit | 0 | — | — |
| **After one anchor edit** | **128** (`endPixel` 289 on a 162-LED channel) | `{128,129,288,289}` | **2 of 4** |
| Control (start stays local) | 0 | `{0,1,160,161}` | 4 of 4 |

**Evidence (HW):** the two resulting payload sets replayed to the bench:

| Path | Wire | Frame buffer |
|---|---|---|
| After anchor edit | base 261 B → 200; one chunk 87 B → 200 | **2 red LEDs at global 256–257**; 288 black. The user marked global 128–129 and 288–289. |
| Control | base → 200; one chunk 103 B → 200 | 4 red LEDs at global **128–129 and 288–289**. Correct. |

Every POST returned 200 in both cases — the device cannot tell the app anything is wrong, and the app does not look (F7).
**Evidence (CODE, citations):** `segment_setup_screen.dart:837-840` (toggle), `:823` (Reset Defaults — same path); `roofline_config_providers.dart:587-598`, `:508-535`; `models/roofline_configuration.dart:278-295`, `:304-309`; `manual_editor/selection_logic.dart:59-71`; `manual_editor/pixel_design_document.dart:53-61`; `manual_editor/design_apply.dart:52-67`; `models/pixel_map_channel.dart:183-186` (split passes segments through verbatim).
**Same silent-failure shape as F7?** Yes, exactly — and F7 is *why* this was reported as "doesn't work" rather than as an error.

#### N1c — The Setup Wizard writes every segment onto channel 1
**User sees:** after an installer runs the wizard on a 2-channel home, **Channel 2** has no runs, no anchors, nothing selectable; Channel 1's feature tools reach past its end.
**Failure mode:** step 2 collects `_selectedChannels` and per-channel LED counts, but `_saveConfiguration` builds each `RooflineSegment` with **no `channelIndex`** (defaults to 0) and a cumulative `startPixel`. `savePixelMap` is also called without `sourceCounts`.
**Evidence (CODE):** `roofline_setup_wizard.dart:37-39`, `:97-113`, `:140-141`. Harness: wizard-shaped config → `segmentsForChannel(0)` = 2, `segmentsForChannel(1)` = **0**; ch1 anchors `{0,1,128,129}` on a 128-LED channel. This plausibly explains the founder's own map in the original audit (ch0 maps **168** px on a 128-LED channel). **NOT VERIFIED** against that document — Firestore was not read in this pass.

#### N1d — The in-app preview has the same defect
`DesignPreview._ledColorsFor` slices `frame[s.channelIndex]` from `s.startPixel` to `s.endPixel`, i.e. channel-local. After N1b's re-base, channel 2's trace is drawn from LEDs 128–161 of a 162-LED channel — the wrong 34 LEDs, the rest blank. So the **on-screen** preview is wrong as well as the lights. **CODE:** `manual_editor/design_preview.dart:157-164`.

### N2 — Architectural › Twinkle renders solid instead of animating  ← independent of A/B/C
**User sees:** Explore → **Architectural Downlighting (White)** → e.g. 3000K → any card → in the tuner, **Twinkle** is the **third "Top Pick"**. They tap it. The house shows a **steady warm white**. No sparkle. Same on the **Galaxy & Starlight › Twinkling Stars** cards whose names promise "1 Solid 2 Twinkle".
**Is it being substituted the way F3 substitutes `fx:83`?** **No.** The tuner's `_effectiveEffectId` only substitutes for `effectId == 0`; Architectural nodes are excluded even from that. The wire carries genuine **`fx:17`**, and the device reports `fx=17` back. **HW.**
**Failure mode — two independent causes, both on the bench:**
1. **Colour-slot semantics.** WLED's Twinkle fades every pixel toward **`col[1]`** (the *background*) and sparkles with the palette. Every Architectural style supplies **two near-identical bright whites** — e.g. 3000K = `#FFB16E` and `#FFCFA0` — and the app sends them as `col[0]`, `col[1]`. So the strip is flooded with white #2 and "sparkles" of white #1 on top. The sparkles are actually *dimmer* than the background.
2. **Speed.** The tuner resets speed to the effect's profile default, **`sx:40`** for Twinkle ⇒ WLED's `cycleTime = 20 + (255−40)×5 ≈ 1.1 s` per new pixel.

**Evidence (HW) — 10 s time series per payload, ~133 frames each:**

| Payload (app-generated, byte-exact) | Lit LEDs per frame | Share of lit samples that are exactly `col[1]` | Frames differing from previous | LEDs that ever changed |
|---|---|---|---|---|
| **Tuner: 3000K "1 On 2 Off" + Twinkle** (`fx17 sx40 ix128 pal5 grp1 spc2`) | **97 / 97 constant** | **≈ 93 %** (11,981 of 12,901) | 5 of 132 | 10 |
| Tuner: "All 3000K" + Twinkle (`spc0`) | **290 / 290 constant** | ≈ 97 % | 6 of 133 | 12 |
| Galaxy › "1 Solid 2 Twinkle – Classic Twinkle" (`sx80 ix180`) | **97 / 97 constant** | ≈ 90 % | 8 of 133 | 14 |
| **Control: identical, `col[1]` = black** | 2 – 6 | 0 % | 2 of 135 | 4 |

Rows 1–3: every lit LED stays lit in every frame, at one colour — **a solid field.** The control proves cause 1 (remove the white background and the field disappears) and exposes cause 2 (what remains is 2–6 LEDs on a 290-LED house, changing about once every 5 s).
**Evidence (CODE):** styles `pattern_repository.dart:890-900`; node metadata `:940-980`; tuner payload `colorway_effect_selector.dart:588-592`, `:644-672`; effect-tap speed reset `:1713-1717`; Top Picks `wled_effects_catalog.dart:907-910`; speed profile `effect_speed_profiles.dart:307`; builder `selector_payload.dart:125-145`; Galaxy cards `pattern_repository.dart:1492-1560`.
**Scope — flagged, not individually traced:** cause 1 is not unique to whites. *Any* 2-colour palette run through Twinkle renders as a **solid field of colour #2** with colour-#1 sparkles; it is merely *invisible* on Architectural because the two colours were chosen to be nearly the same. Other effects that use `col[1]` as background are likely affected the same way. **NOT VERIFIED** beyond `fx:17`.
**Side-finding (CODE, low):** the Architectural card list `[0, 2, 12, 6, 15, 51, 46, 41]` is commented *"…Gradient, Twinklefox, Lighthouse"* but on 0.15.1 **`51` = Fairytwinkle and `46` = Gradient**. The same file's `kColorwayEffectIds` was re-numbered for exactly this drift (`:149-153`, *"old 46 rendered Gradient, not Twinklefox"*); this list was missed. Users see the true catalog names ("…- Fairytwinkle", "…- Gradient"), so it is an intent bug, not a labelling bug. `pattern_repository.dart:1282-1284`.

### N3 — Changing "4 off, 1 on" to "6 off, 1 on" collapses / needs manual re-selection

**Headline: the symptom as literally worded — exactly *one* light after a spacing change — was NOT REPRODUCED on any path.** Four separate defects were found on the surfaces where a user can attempt this, plus one surface that works. Reported precisely so the fix pass does not have to guess which screen the reporter was on.

#### N3-ok — The Explore adjustment sheet's Spacing slider works (HW)
Apply Architectural **"1 On 4 Off"**, open the card's adjustment sheet, drag **Spacing** to 6. The app sends only `{"seg":[{"id":0,"spc":6,…},{"id":1,"spc":6,…}]}`; the chokepoint does **not** reset `grp` for a partial payload (`wled_payload_utils.dart:585-595`).
**HW:** before — seg0 **26**/128, seg1 **33**/162, lit at 0,5,10,15…; after — seg0 **19**/128, seg1 **24**/162, lit at **0,7,14,21…**. Device reports `grp=1 spc=6`. **Correct.** `pattern_grid_widgets.dart:2049-2062`, `:2410-2422`.
*(Low, CODE: Grouping and Spacing share one 200 ms debounce timer, so moving both within 200 ms drops the first change — `:2050-2051`.)*

#### N3a — Manual editor: Every-Nth is add-only and remembers nothing  ← same family as F2
**User sees:** they painted every 5th LED with **Every-Nth**. To widen it they open Every-Nth again. The sliders are back at **Start 0 / End (last) / Every 3** — not what they used. They set Every = 7, **Select**, **Paint**. The old every-5th LEDs are **still lit**; they now have a jumble. The only way out is to erase the old pixels — and on a strip where each LED is ~2 px wide (F2), that means picking them out one at a time.
**Failure mode:** `_everyNthDialog` calls `_addAll` (**adds to** the selection, never replaces); `paint` only ever adds overrides; painting does not clear the selection; the dialog's `start/end/step` are **locals re-initialised on every open**; the document stores pixels, not "a pattern", so there is nothing to *adjust*.
**Evidence (CODE, real classes):** every-5th = **26** LEDs; re-run with 7 and paint → **41** lit (`0,5,7,10,14,15,20,21,25,28…`); a clean every-7th is **19**. `manual_design_editor.dart:158-187` (locals `:162`, `_addAll` `:178`), `:134-137`, `:87-94`; `selection_logic.dart:12-24`.
**Most likely source of the literal "one light" — NOT CONFIRMED:** the dialog's three sliders are labelled only **Start / End / Every**, with no on/off vocabulary and no count preview. `everyNthInRange(start:0, end:6, step:7)` returns **`[0]`** — a single LED. A user who reads "End" as the *off count* and sets it to 6 gets exactly one light. This is the only route found to a single-LED result. **Ask the reporter which screen they were on.**

#### N3b — Spacing cannot be saved into, or edited on, a design at all  ← root cause A
**User sees:** they like "1 On 4 Off", save it (Current Colors → save as pattern), and later apply it from **My Designs** — **every LED is on.** Or they open a saved design with **Edit**: the tuner shows **"LEDs per color" 1–5** (that is `grp`, the *on* count) and **no control for the off count**.
**Failure mode:** `ChannelDesign` has **no `grp`/`spc` field**. The tuner's own comment: *"`grp` / `spc` are not written either… `ChannelDesign` has no field for them."* `_seedFromDesign` builds its `SelectorState` without them (defaults `grp:1, spc:0`); `toWledPayload()` asserts `kDesignSpacingDefaults`; the only writer of `selectorSpacingProvider` is `initState`.
**Evidence (CODE):** `colorway_effect_selector.dart:348-357`, `:410-413`, `:300` (sole writer; grep-confirmed), `:1853-1901`; `design_models.dart:268-272`, `:348-358`; `current_colors_provider.dart:250-273`.
**Related dead UI (low):** `PatternAdjustmentPanel` has Grouping/Spacing sliders (`:504-540`) but its only mount passes `showPixelLayout: false` (`wled_dashboard_page.dart:1162`) — unreachable.

#### N3c — AI studio: word order, commas, and "off" = black
**User sees:** in AI mode, *"warm white 1 on, 6 off"* or *"6 off 1 on"* → **every LED lit**, spacing ignored. *"warm white 1 on 3 off"* → a pattern that is **completely dark.**
**Failure mode:** the spacing regex is `(\d+)\s*on\s*(\d+)\s*off` — on-first only, and `\s*` cannot cross a comma. Separately the colour table maps **`'off'` → black** (`'black': ['black','off']`), so a clause with two colour words plus "off" gets `accentColor = black`, and the composer paints the *on* LEDs with the accent.
**Evidence (CODE, real NLU → solver → composer, 128-LED run):**

| Prompt | Parsed rule | Result |
|---|---|---|
| `warm white 1 on 6 off` | pattern 1/6 | needs clarification (see N3d) |
| `warm white 1 on, 6 off` | **none** | 128/128 lit |
| `warm white 6 off 1 on` | **none** | 128/128 lit |
| `warm white every 7` | everyNth 7 | 19/128 lit, `[255,255,255,0]` ✔ |
| `warm white 1 on 3 off` | pattern 1/3 | 32 groups, **all `[0,0,0,0]`** — dark |
| `red 1 on 3 off` | pattern 1/3 | 32 groups, `[255,0,0,0]` ✔ |

`nlu_service.dart:326` (regex), `:743` ("off"); `pattern_composer.dart:336-338`. Also: "warm white" parses as pure `#FFFFFF`.

#### N3d — AI studio: "keep what I asked for" loops; "Set manually" is dead  ← F1
**User sees:** *"The spacing doesn't quite work — which option looks best?"* They pick **"1 on, 6 off (with remainder)"**. **The same question comes back.** They pick **"Set manually — Open spacing controls"**. **Nothing opens.**
**Failure mode:** the "original" option re-submits the same rule, which fails the same divisibility check (`remainder <= onCount`) and re-raises the ambiguity. Several *stretch/compress* alternatives fail it too (128 px: for 1/4 only "1 on, 3 off" resolves; for 1/6 only "1 on, 7 off"). "Set manually" → `onManualRequested` → `_showManualControls = true` — **F1's flag that nothing reads.**
**Evidence (CODE):** `constraint_solver.dart:115-165`; `clarification_service.dart:500-527`, `:269-274`; `ai_design_studio_screen.dart:126-128`. Harness: `original` → `needsClarification [spacingImpossible]` for both 1/4 and 1/6, on both a single-run and a 5-segment config.

### N4 — RESOLVED: "Editing pre-existing patterns — you can save them or apply them"

**Definitive answer: the note is correct as written — it *works* — for the editor path. It is not missing a "can't". But the same design applied from My Designs is still broken, which is F3, not a new finding.**

### N5 — RESOLVED: "Color slider is bad, needs to be a color wheel"

**The screen is `EditPatternScreen` (`/edit-pattern`), reached from the Explore tuner's ⚙ "Open in Pattern Editor" icon** (`colorway_effect_selector.dart:976-992` — a 44 px `Icons.tune` button; this is the **only** entry point, grep-confirmed).

Its colour section has three tabs (`edit_pattern_screen.dart:632-681`):

| Tab label | What it actually is | Lines |
|---|---|---|
| Common Color | swatch grid | `:676` |
| **"Color Picker"** | **not a picker — three sliders:** a hue bar (`Slider` 0–360 over a gradient) + **Sat** + **Val** | `:715-790` |
| **"Slider"** | three more sliders: **R / G / B** | `:792-…` |

So a user who taps "Color Picker" expecting a wheel gets sliders. That is the report.

**A concrete defect that makes the slider genuinely bad (CODE, proven):** `_buildHsvPicker` recomputes `hsv = HSVColor.fromColor(currentColor)` **on every build** (`:726`) instead of holding HSV state. HSV→RGB→HSV loses hue whenever saturation or value hits 0: drag **Sat → 0** and hue snaps **200° → 0°**; drag **Val → 0** and back, and a blue comes back **white**. The hue thumb jumps to red by itself.

**The app already owns a colour wheel.** `lib/features/wled/widgets/neon_color_wheel.dart` (`NeonColorWheel`) is mounted in `current_colors_editor_screen.dart:501` and `patterns/color_sequence_builder.dart:242` (each pairs the wheel with a brightness slider — reasonable). No third-party picker package is in `pubspec.yaml`.

**Sweep of every other colour UI named in the brief — no slider-based colour picker in any of them:**

| Surface | Colour input |
|---|---|
| Manual pixel editor | 11 fixed swatches (original audit F2 / P2-9). Its only `Slider` is the Every-Nth dialog's number rows (`manual_design_editor.dart:193`). |
| AI Design Studio mode | none — colours come from text |
| Colorway Effect Selector (tuner) | **no colour editor at all** (its own comment, `:410-411`); sliders are speed / intensity only |
| `design/widgets/effect_selector.dart` | speed/intensity sliders; **0 mounts** — dead code, as the original audit noted |
