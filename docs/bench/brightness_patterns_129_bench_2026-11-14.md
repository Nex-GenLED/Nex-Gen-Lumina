Run from session f37ad124 against the spare `192.168.1.179` (WLED 0.15.4 vid 2508020, esp32, 300 LEDs = 3 buses × 100, all SK6812 RGBW type 30, auto-white off) and the home `.150` (WLED 0.15.1 vid 2507300, esp32, 490 LEDs = buses 128 / 162 (bus `rev`) / 100 / 100, type 30; buses 2 and 3 have auto-white `rgbwm` 1 and 3). ## Preconditions and reads
- Spare idle check: `/json/state` at 22:07:15Z and 22:07:45Z were identical (no other user). `/json/info` `ws: 0`.
- Both controllers: `light.gc = {bri 1, col 2.8, val 2.8}`, `light.pal-mode 0` (linear palette blend), palette 4 is `* Color Gradient` on both (`/json/pal`; the brief's "Colors Gradient"); `fxcount 187`.
- `/json/live` returns `{"error":4}` on both, so pixels were read through the `/ws` live view (`{"lv":true}` → binary `L,1,` + RGB triples). On a classic ESP32 `MAX_LIVE_LEDS_WS` is 1024, so every LED is served (300/300 and 490/490 triples, verified). The live view is the post-gamma colour, not scaled by master `bri`, and adds W into RGB with `qadd8`: on the home controller's auto-white buses 2 and 3 every white reads 255 (saturated), so only buses 0 (128) and 1 (162) are measurable there.
- White on the wire = mixed RGB `[v,v,v,0]`. The palette path cannot ramp W at all: `color_from_palette` returns `W(col[0])` for every pixel. The app's gradient colours already force W = 0 (`colorsToWledCol`). A value `v` lights at `255·(v/255)^2.8`; 40 % light needs `v = 184`, 92.5 % needs `248`, 70 % needs `224`.
- Levels below are `lit / 255 · 100` of the red channel (white → all channels equal). Intended V: `100 − 60·(1 − |1 − 2·phase|)`, phase = `(p mod N)/N`, so N = 6 gives 100/80/60/40/60/80 (T1) and N = 18 gives 100 → 40 over 9 pixels and back (T2).

## 2. How N (cycle in pixels) maps to Size (`ix`)
`mode_palette` (identical source in 0.15.1 and 0.15.4): `colorIndex = floor(x·255/(len−1))`, then for `ix > 128` `colorIndex = (ix−112)·colorIndex ÷ 16` (integer), wrapped to 8 bits; one palette repetition = 256 index units. So **cycle N = 16·256·(len−1) / (255·(ix−112)) ≈ 16.06·(len−1)/(ix−112)** pixels and **`ix = 112 + 16.06·(len−1)/N`**, capped at 255. The smallest cycle a bus can show is 16.06·(len−1)/143: **11.1 px on 100 LEDs, 14.3 px on 128, 18.1 px on 162**. Shift (`sx`, `o1 false`) subtracts colour-index units: a half-cycle is `sx 128` (the run starts at the trough); one pixel ≈ `(ix−112)·255/(16·(len−1))` units.

## 3. Restart at each bus start and at the run end
Every segment runs its own instance (one effect per segment): with `sx 0` **every bus starts at phase 0 (lit 255 = 100 %)** on both controllers, and the cycle is cut wherever the bus ends — e.g. spare N = 18: last pixel (99) lit 109 = 43 % (phase 99 mod 18 = 9 → the trough); N = 12: last 170 = 67 %; N = 30: last 163 = 64 %. There is no continuity across a bus boundary. With the app's transport (`applyChannelFilter` copies ONE segment template to every channel) a single `ix` reaches every bus, and because N depends on the bus length the cycle differs per bus: home E5 (`ix 225` everywhere) measured 18.17 px on the 128 bus, 22.83 on the 162 bus and 14.17 on the 100 buses.

## 7. Judgement against T1 / T2 and the decision rule
- **T1 (6-pixel cycle): not reproducible by fx 65 on either firmware.** The Size slider caps the cycle at ≈ 16.06·(len−1)/143 pixels (11.1 px on a 100-LED bus, longer on longer buses); N = 6 and N = 9 need `ix` > 255 on every bus of both controllers. A 6-pixel cycle also has five distinct levels, more than the three colour slots can state.
- **T2 (18-pixel cycle): reproducible within 3 pp only with a compensated slot 0 (95–96 % light), only on buses whose length allows an exact 18 (100 and 128 LEDs; not 162), and only if each bus gets its own `ix`** — the app sends one `ix` to every bus. With the slots exactly as the brief specifies (100 / 40 / 100) it misses by 5.9–6.3 pp on both firmwares.
- Firmware was not the limiting factor: 0.15.1 and 0.15.4 rendered the same numbers for the same bus length.
- **Decision (rule: "if on neither, per-pixel only"):** triangle and ramp patterns use per-pixel `i` data. The palette path stays documented here as a possible later option for long cycles (≥ ~16·(len−1)/143 px) with per-bus Size and a 92.5–96 % slot 0.
