# Design Studio — Forensic Audit (2026-09-19)

**Scope:** Design Studio + pattern saving/editing. **Mode:** read-only audit; nothing was fixed.
**Code pin:** `origin/release/store-submission-consolidated` @ **`995d9fc`** (fetched at audit start), in an isolated worktree. The release-100 branch was not touched.
**Hardware:** bench controller `192.168.1.150` — WLED 0.15.1, vid 2507300, MAC `80f3daae6f04`, 290 RGBW LEDs, seg0 = 0–128 (128 LEDs), seg1 = 128–290 (162 LEDs).
**Firestore:** production project, **read-only** (gcloud ADC). Live ruleset `fdaecb9d`.

## 1. Direct answer to the founder's claim

> "There is no pixel by pixel control at all available."

**Verdict: PARTIALLY TRUE — true as experienced, false as engineered.**

**What is false about it.** True per-pixel control exists end to end and works on hardware. The data model stores a color per LED, the transport uses WLED's per-LED `seg[].i` API (the correct mechanism — this is *not* a segment-level fake), and the bench rendered every painted pixel on exactly the right LED (**HW**, §4 T1): single pixels at LEDs 10/20/30, an every-4th run, and channel 2's local index 0 landing correctly on global LED 128. **The feature is not structurally impossible. No transmission-layer rewrite is needed.**

**What is true about it.** A real user is very unlikely to ever get a per-pixel result, because of five independent defects stacked in front of the working engine:

1. The studio opens in **AI mode**; the pixel editor is behind a small `AI | Manual` toggle in the title bar. The button that is actually *labelled* "Manual controls" is **dead** (F1).
2. In the editor, each LED is drawn **~2 px wide** on a phone. A fingertip covers ~18–22 LEDs. You cannot aim at, or see, a single pixel (F2).
3. Painting is **select-then-press-Paint**, not tap-to-paint; tapping a pixel only draws a selection ring that is nearly the same cyan as the default paint color (F2).
4. If a user does save a design and later applies it from **My Designs**, it goes through a *different, lossy* code path that discards every pixel position and all but ~1 color — the lights go **mostly dark** while the app says "Applied" (F3, **HW**).
5. The feature-based tools (All corners / All peaks / Smart Presets) silently do nothing, because **no production pixel map contains a single corner or peak** (F4/F5, **DATA**).

**The strongest single piece of evidence that the founder's experience is the norm:** of **14 saved designs across 7 users in production, zero are per-pixel** (10 effect, 4 AI-composed) — including the founder's own account (**DATA**).

## 3. Verified-broken findings

Each finding leads with **what the user sees**, because that is what user reports will be matched against.

### F1 — The "Manual controls" button does nothing
**User sees:** In Design Studio they look for manual/pixel control. There's a sliders (tune) icon top-right with the tooltip **"Manual controls"**. They tap it. **Nothing happens** — no panel, no message. Same for "open manual" inside the AI understanding panel, and the manual option in the AI clarification dialog. A reasonable user concludes there are no manual controls.
**Failure mode:** `_showManualControls` is **written in 4 places and read in 0**. It has no effect on `build()`.
**Evidence (CODE):** `lib/features/design/screens/ai_design_studio_screen.dart` — declared `:39`; written `:117`, `:127`, `:208`, `:523`; tooltip `:209`. `grep` confirms no read site. `_handleEditLayer` (`:521-525`) carries a `// TODO: Focus on the specific layer in manual controls`. Flag dates to commit `b5cda7b`.
**Note:** the *real* editor is reached only via the `AI | Manual` `SegmentedButton` in the app-bar title (`:179-192`); the screen defaults to AI (`:42`).

### F2 — You cannot target a single pixel in the paint editor
**User sees:** In Manual mode there is one thin horizontal bar (34 px tall) representing the whole channel. Each LED is a sliver about **2 pixels wide**. Tapping it selects *some* LED near their finger — they can't tell which, and can't hit a specific one. Tapping does **not** color anything; it only adds a thin cyan ring (which, on a 2-px sliver, is wider than the sliver itself). Nothing changes color until they separately press **Paint**. If they use the default color (cyan `#00E5FF`), painted pixels are nearly indistinguishable from the selection ring (`#00D4FF`). Dragging selects a range, but dragging *back* does not shrink it. There is no zoom, no pinch, no scroll, and no way to type an LED number (except inside the Every-Nth dialog). There are exactly **11 fixed color swatches and no color picker**.
**Failure mode:** `_SelectionStrip` lays the entire channel into the available width: `cell = width / length`. On a ~320 px usable width: bench channel 1 (128 LEDs) = **2.5 px/LED**; channel 2 (162 LEDs) = **1.98 px/LED**, minus 0.6 px margins. A ~44 px fingertip spans ~18–22 LEDs.
**Evidence (CODE; lengths HW-measured):** `lib/features/design/manual_editor/manual_design_editor.dart` — strip `:453`, `cell` `:477`, fixed `height: 34` `:495`, `onTapDown` toggle `:486`, add-only `_selectRange` `:126-132`, palette loop `:395`, default paint `:42`. Palette = 11 entries, `smart_preset_models.dart:85-97`.
**Why it matters most:** this is the defect that most literally matches *"no pixel by pixel control."* The engine is per-pixel; the only input surface for it is, in practice, a coarse range selector.
**Secondary (low):** `onTapDown` (not `onTap`) means a finger resting on the strip while scrolling the page vertically can toggle a pixel unintentionally.

### F3 — A saved per-pixel design applied from My Designs turns the lights (mostly) dark  ← highest-impact
**User sees:** They paint a design, press **Apply to Lights** *inside the editor* — it looks right. They **Save**. Later they open **My Designs → their design → Apply to Lights**. The app shows **"Applied: <name>"**. The house goes **almost entirely dark**, possibly with one solid block of a single color at the far end of a long run — in a place they never painted. All other colors are gone. Nothing indicates an error.
**Failure mode:** there are **two different "apply" implementations**:
- Editor Apply → `applyBaseAndSpans` → per-pixel spine. Correct.
- My Designs Apply → `applySavedDesign` → `CustomDesign.toWledPayload()`, which keeps only the **first 3 color groups**, **discards every `startLed`/`endLed`**, and substitutes **`fx:83`**. WLED's fx 83 draws `sx+1` LEDs of `col[0]` then `ix+1` LEDs of `col[1]` (`col[2]` unused). Designs default to `sx=ix=128` → 129 LEDs of `col[0]`, then `col[1]`.
- Compounding it: `_save()` stores **full-coverage** groups, so the *first* group is almost always the unpainted base `[10,10,12,0]` — which renders as **black**. So `col[0]` = black for the first 129 LEDs of every channel.

The detail screen *knows* the design is per-pixel (it routes **Edit** correctly on `kind`), but its **Apply** button ignores `kind`.
**Evidence (HW):** the *same* saved design (87 painted pixels, 6 colors, 2 channels):

| Path | Wire payload | Frame buffer |
|---|---|---|
| Editor Apply | `i:[10,[255,0,0,0], 20,[0,255,0,0], 30,[0,60,255,0], 40,50,[255,40,150,0], 60,[…amber], 64,…]` | 6 colors, every pixel on the correct LED |
| My Designs Apply | `col:[[10,10,12,0],[255,0,0,0],[10,10,12,0]], fx:83, sx:128, ix:128` | **257 LEDs black + one 33-LED red block at 257–289** |

Green, blue, pink, amber, purple: gone. The red block sits where the user painted nothing.
**Evidence (CODE):** `design_models.dart` `toWledPayload()` `:244`, `.take(3)` `:252`, `? 83` `:265`. `apply_saved_design.dart:57` (self-described "Canonical 'apply a saved design' routine"), success toast `:96`. `design_detail_screen.dart:271` (Apply, no `kind` branch) vs `:288-290` / `:343-355` (Edit, branches on `kind`).
**Other callers of the same lossy function** (not individually traced — flagging for the fix pass): `scenes/scene_models.dart:237`, `scenes/scene_providers.dart:140`, `wled/pattern_theme_selection.dart:320`, and the schedule path referenced at `colorway_effect_selector.dart:339`. **A per-pixel design placed in a Scene or a Schedule will very likely degrade the same way. NOT VERIFIED.**

### F4 — The pixel map mixes two index bases; the staleness check can't detect it
**User sees:** On a multi-channel home, on **Channel 2+**: tapping **All runs** selects **nothing** (or the wrong stretch of LEDs); smart-preset accents never appear on that channel. No error. Channel 1 looks fine, which makes it seem intermittent.
**Failure mode:** `RooflineConfiguration.recalculateStartPixels()` runs **one cumulative counter across all segments regardless of channel**, so channel 2's first segment gets `start_pixel` = (channel 1's total). Every consumer (`featureIndices`, `anchorIndices`, `accentSpansForChannel`) treats `start_pixel` as **channel-local**. `splitConfigToPixelMapChannels` passes segments through verbatim (no re-base). `isStaleAgainst` compares only `sourcePixelCount` to the live bus length — never whether segments *fit inside* the channel.
**Evidence (DATA, production):** of 7 channel≥1 docs, **5 store cumulative offsets** (33, 44, 41, 40, 44) and 2 store channel-local 0. Example: a user's ch1 has `start_pixel=41, pixel_count=41` on a 41-LED channel → indices 41–81 → **100% out of range** → silently dropped by `PixelDesignDocument.paint` (`:58`). **9 of 28 docs** have mapped totals ≠ device truth; **all 28 report `is_stale=False`**. The founder's own map: ch0 maps **168** px on a **128**-LED channel; ch1 maps 128 on a 162-LED channel (LEDs 128–161 of channel 2 unreachable by feature tools).
**Evidence (CODE):** `models/roofline_configuration.dart:278-296` (dates from the initial commit — predates the per-channel map); `models/pixel_map_channel.dart:74-75`, `:167-197`; `manual_editor/selection_logic.dart:40-50`.

### F5 — Smart presets and feature-selection tools are silent no-ops for every production user
**User sees:** On the dashboard they tap **Corner Accents** (or Peak Highlights / Feature Outline). The house turns **one plain solid color with no accents at all**, and the app reports success. In the editor, **All corners** and **All peaks** select nothing, with no message.
**Failure mode:** all three presets require a segment of `type` corner/peak/non-run, or an `architectural_role`. The "no map" guard only checks `segments.isEmpty`, so a run-only map passes, compiles to **zero accent spans**, and the shared spine paints just the base.
**Evidence (DATA):** 28 pixelMap docs / 31 segments fleet-wide → **`type` is `run` for 31 of 31. Zero corners, zero peaks.** The field `architectural_role` is **absent from all 31**. Only 6 segments carry any anchor data.
**Evidence (CODE):** `smart_presets/smart_preset_logic.dart:19-30`; guard `smart_preset_apply.dart:38-39`; `selection_logic.dart:40-50` (empty set → `_addAll(ch, {})` → no-op).

### F6 — A failed Save shows nothing
**User sees:** They press **Save** (and, for a new design, name it). The buttons grey out briefly and come back. **No "Saved" toast, no error.** The design is not in My Designs.
**Failure mode:** `_save()` is `try { … } finally { … }` with **no `catch`**. `DesignService.createDesign/updateDesign` **rethrow**. Any Firestore error escapes as an unhandled async exception. Also `if (uid == null) return;` exits silently.
**A concrete, currently-live trigger (CODE + live rules):** `_save()` writes to `effectiveUserUidProvider`. In installer **Existing Customer** mode that is the *customer's* uid while `auth.uid` is the staff uid. The live `designs` rule is `isOwner(userId)` only — unlike `pixelMap`, it has **no `staffMayReach` clause** — so the write is denied, silently. *An installer demoing Design Studio on a customer's account cannot save, and is told nothing.* Second trigger: editing a design that was deleted elsewhere → `.update()` throws on a missing doc.
**Evidence:** `manual_design_editor.dart:273-334` (`finally` at `:331`, no catch); `design_service.dart:19-40`; `installer/installer_access_providers.dart:39-49`; live rules `:1044-1049` (designs) vs `:506-510` (pixelMap). **NOT VERIFIED at runtime** — no client credential available; per project practice an admin write would prove nothing about app-writability, so none was attempted.

### F7 — Editor "Apply to Lights" reports success even when the device writes fail
**User sees:** Green **"Applied to your lights"** — but the lights didn't change, or only the dark base arrived and none of the painted pixels. Live preview fails with no feedback at all.
**Failure mode:** `applyBaseAndSpans` `await`s `repo.applyJson(...)` and `writer.applyPerPixel(...)` and **discards both booleans**, then `return true`. It returns false only if there is no repo or no effective channels. `_scheduleLivePreview` doesn't await or inspect anything.
**Evidence (CODE):** `manual_editor/design_apply.dart:52`, `:58`, `:67`; `manual_design_editor.dart:213-219`, `:221-240`. Affects all three callers of the shared spine (editor, AI studio Apply, smart presets).

## 5. Root-cause analysis

**There is no single root cause. There are three independent causes, and the engine itself is not one of them.**

**Root cause A — two generations of "design" coexist, and only some doors lead to the new one.** (F3, F1, and the dead providers.)
The original model was *"a design = up to 3 colors + a WLED effect per channel"* (`toWledPayload`). Slice 0–4 added a genuine per-pixel model *on the same `CustomDesign` class*, reusing `colorGroups` to mean "positional runs". The new editor's Apply was wired to the new spine; the **older apply/scene/schedule consumers were never migrated**, so they reinterpret positional runs as "a list of colors" and take the first three. The same generational seam explains F1 (a manual-controls flag from the pre-Slice-4 screen whose panel was removed) and the dead `saveDesignProvider` / `applyDesignProvider` / `EffectSelector` (0 mounts). **This is the cascade to fix first: one data shape, two incompatible readers.**

**Root cause B — the pixel map has the same seam, one layer down.** (F4.)
`recalculateStartPixels()` predates per-channel maps and numbers LEDs cumulatively across the whole home. Slice 1 split storage per channel and Slice 3/4 consumers assume channel-local indices, but the old writer was kept and nothing re-bases. Same pattern as A: a new reader bolted onto an old writer with no translation and no validation.

**Root cause C — the input UI was never sized for real channel lengths.** (F2.) Independent of A and B. The strip works in tests and on a 20-LED demo; at 128–162 LEDs it is unusable. Nothing structural — but it is the defect the founder is most directly describing.

**Cross-cutting aggravator — success is reported without checking.** (F5, F6, F7, and F3's toast.) Every one of these failures is *silent*. None of them causes the others, but this is why they survived: no path ever told a tester something went wrong.

**On the "orphaned feature" question:** Design Studio does **not** share the Welcome Home / old-commercial-shell defect. The pixel map has real consumers (editor selection tools, smart presets, staleness provider, installer→customer handoff migration). It is **starved, not orphaned** — the consumers exist but the data they need (corners/peaks) has never been produced in production, because the capture step is optional (`map_roofline_step.dart:22`) and customer self-mapping yields a single run.

## 6. Other investigated items

- **Save vs edit — one path or two?** One. `_save()` handles both; carrying `existing.id` routes `saveDesign` to `updateDesign` (`design_service.dart:43-49`). `copyWith` preserves tags/description/`composedPattern`. **No divergence here — the divergence is in *apply*, not save (F3).**
- **Reload fidelity:** lossless (0/290 mismatches). One benign artifact: after reopen, `paintedCount` reads 290 instead of 87, because full-coverage save makes every base pixel an "override". No functional effect found (`_maybeAdd` skips base-colored runs).
- **`DesignKind` misclassification (low):** classification is by shape — per-pixel iff some channel has >1 group. A manual design painted *entirely one color* (or saved blank) is classed `effect`, so **Edit opens the colorway tuner instead of the paint editor.** `design_detail_screen.dart:60-65`.
- **AI-composed designs cannot be edited** — button disabled with on-screen text "not wired yet" (`design_detail_screen.dart:288-290`, `:304-313`). Honest in the UI; noting for completeness.
- **Unpainted = dark.** The editor base is hard-coded `[10,10,12,0]` (`:37`), which renders as **black** on hardware (T1). There is no UI to change it, so any manual design lights *only* the painted pixels.
- **Shared code with the Explore preview work — flagged, not modified:**
  - `design_detail_screen.dart:11` imports `colorway_effect_selector.dart`; **Edit** on an effect-kind design opens `ColorwayEffectSelectorPage.forDesign(design:)` (`:349-351`). Any change to that page changes Design Studio's edit flow.
  - `apply_saved_design.dart` deliberately mirrors `ColorwayEffectSelectorPage._applyPattern` (its header cites `colorway_effect_selector.dart:213-345`).
  - F3's `fx:83` substitution is the *same* fx-83 positional-block semantics addressed by the recent `solid_palette_blocks.dart` work. `solid_palette_blocks.dart` and `effect_preview_widget.dart` are **not** imported anywhere under `lib/features/design/`.
- **Remote (off-LAN) per-pixel:** each chunk is one `applyJson` relay command. Structurally fine, but at the documented ~5–10 s per command a 2-channel apply is ≥3 sequential commands, and live preview (300 ms throttle) would flood the queue. **NOT VERIFIED** — exercising it would have meant driving the production relay.

## 7. What would need to be true for this to work as marketed

Conditions, not fixes. In priority order.

**P0 — without these, a user cannot get a per-pixel result they can keep.**
1. **Every path that sends a saved per-pixel design to a device must preserve per-LED positions and all colors** — My Designs apply at minimum, and scenes and schedules if designs can be placed in them. (F3)
2. **A user must be able to see and hit one specific LED** on a channel of realistic length (100–300 LEDs). (F2)
3. **The pixel editor must be reachable by the control that says it is**, and should not require discovering a title-bar toggle. (F1)

**P1 — without these, it works but lies or misleads.**
4. **Save and Apply must report what actually happened** — failures surfaced, device-write results checked. (F6, F7)
5. **Whoever is allowed to open a customer's Design Studio must be allowed to save in it** (or be told they can't). (F6)
6. **One index base for the pixel map**, with existing production docs reconciled, and a validity check that catches segments that don't fit their channel. (F4)

**P2 — without these, the "smart" half of the marketing is empty.**
7. **Pixel maps must actually contain architectural features** for the homes that are sold this — which means the capture step can't be both optional and the only source. (F5)
8. **Feature tools and smart presets must say so when there is nothing to act on**, instead of painting a solid and reporting success. (F5)
9. **A user needs more than 11 fixed swatches and a black background** if the promise is "any color, any pixel". (F2)

**Needs evidence before it can be prioritised:** remote/bridge per-pixel latency and reliability; per-pixel designs inside Scenes and Schedules (including the known `psave`-captures-`frz` hazard); all UI findings, on a real handset.

## 9. Side-finding (out of scope, pre-existing, untouched)

The bench controller's `/presets.json` (16,585 B) **is not valid JSON**: it contains **7 stray non-ASCII bytes** inside whitespace-padding regions (first at byte 3868). Byte-identical before and after this audit, and this audit never wrote presets, so it **pre-dates** this work. Individual presets (e.g. preset 2) parse fine and WLED evidently tolerates it, but any strict parser — including app code that `jsonDecode`s the whole file — would throw. Worth a look in its own right.
